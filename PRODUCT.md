# Agent OS product context

## Register

product

## Users

The current development environment is used by the founder to test a complete Linux-based agentic operating system. The broader initial audience has not yet been selected. The long-term interaction model must support everyday computing without requiring the user to understand Linux internals.

## Product Purpose

Create an operating system whose agent can understand and act across the environment, using a general system broker. Intelligence begins with input and extends through activities, applications and system services. The current terminal environment is a delivery stage; the intended product includes a custom graphical environment.

## Brand Personality

Calm, welcoming, beautiful. The founder explicitly requires beauty and high usability, with macOS as a benchmark for integrated craft without copying its visual identity or interaction conventions wholesale.

## Anti-references

A conventional desktop with a chatbot attached. A developer-only interface that treats roughness as the price of intelligence. Canned demonstrations that imply capabilities the system does not possess. A copy of the macOS desktop. An interface that requires a separate intent category for every user question.

## Design Principles

1. Treat beauty, usability and responsiveness as architectural requirements.
2. Give the person and the agent shared control through a coherent environment model.
3. Make voice a first-class input path while preserving effective non-voice operation.
4. Maintain continuity across activities, processes, conversations and client sessions.
5. Make tiling a first-class capability in the terminal. GUI tiling remains a separate design decision.
6. Give the GUI equally considered light and dark appearances, with a minimal system bar and no dock. The bar shows date/time, the signed-in user and an agent-status entry that opens a standalone Agent Monitor window.
7. Provide an agentic launcher accessible through voice, keyboard and mouse, with clear visible feedback while receiving and acting on instructions.

## Accessibility & Inclusion

The white paper requires accessibility from the beginning and essential operation when speaking is impossible or undesirable. Mouse and keyboard are explicitly first-class for accessibility and personal choice; voice is not mandatory. Specific user accommodations and formal conformance targets remain unspecified. Input alternatives, legibility, identifiable focus, non-color status cues and error recovery are design requirements; implemented accessibility must be evaluated rather than assumed.

## Agent authority

The agent acts on behalf of the user across the operating system. Routine non-destructive work should proceed without approval, regardless of whether it needs root or involves development tools. User approval protects against destructive effects and loss of work/access. Uncertain effects require inspection; the model's own claim that an action is safe is not authority. External account authentication is a separate user-participation step.
